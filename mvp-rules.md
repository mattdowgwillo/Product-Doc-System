# MVP Rules

## Purpose

Prevent scope creep and overbuilding during product development.

---

# Core MVP Philosophy

The goal of MVP is:

- validate the core value
- test real behavior
- learn quickly
- reduce complexity
- enable iteration

MVP is NOT:

- completeness
- flexibility for every edge case
- final architecture
- maximum feature count

---

# Core Rules

## 1. Build the smallest valuable version

Only build what is required to prove:

```text
Does this product solve a meaningful problem?
```

---

## 2. Avoid premature flexibility

Do not build:

- advanced settings
- excessive customization
- generalized systems too early

---

## 3. Prefer real behavior over perfect structure

Real usage teaches more than speculation.

---

## 4. Keep AI instructions simple

Overly detailed prompts increase drift and inconsistency.

---

## 5. Reusable systems must earn their complexity

Do not create reusable abstractions until repetition is proven.

---

## 6. One clear workflow beats many optional workflows

Optimize for clarity first.

---

## 7. Complexity must be justified by user value

Every added feature should answer:

```text
What real user problem does this solve right now?
```

---

# Common MVP Failure Modes

- too many features
- too many states
- over-documentation
- building future ideas too early
- adding flexibility before validation
- optimizing before usage exists

---

# Product Documentation Rule

Only create a new doc if:

- a new page exists
- a reusable component exists
- a new flow exists
- a true system-level concept exists

---

# Final Principle

Simple systems learn faster.
